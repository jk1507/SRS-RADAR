4. Most important: DON'T make the system keyword-based
This is the biggest change from your current prototype.
Suppose the SRS contains:
Requirement A
The system should respond quickly when a doctor opens a patient's medical image.
A keyword system sees:
"quickly"
and says:
AMBIGUOUS
That's weak.
Your system should understand:
Actor:
Doctor

Action:
Open medical image

System behavior:
Display image

Performance constraint:
Unspecified

Measurable threshold:
Missing

Condition:
Patient image access

Potential quality issue:
Performance requirement not objectively testable
That is semantic requirement analysis.

5. Requirement understanding using LLM
For every requirement, send structured context to the LLM.
For example:
{
  "requirement_id": "REQ-024",
  "section": "2.1 Diagnostic Latency",
  "text": "The system should provide fast response for emergency medical image rendering.",
  "document_context": "...",
  "neighboring_requirements": [
    "REQ-023 ...",
    "REQ-025 ..."
  ]
}
The LLM should return structured information such as:
{
  "requirement_type": "non_functional",
  "category": "performance",

  "actor": "doctor",

  "action": "render emergency medical image",

  "condition": "emergency diagnostic workflow",

  "constraints": [],

  "measurable": false,

  "ambiguities": [
    {
      "phrase": "fast response",
      "reason": "No measurable latency threshold"
    }
  ],

  "missing_information": [
    "maximum response time",
    "concurrent user load"
  ],

  "testability_score": 42,

  "confidence": 0.94
}
This is where your LLM actually becomes useful.
OpenAI's API supports structured JSON-schema outputs, which is exactly what you want for turning free-form SRS text into predictable analysis objects rather than parsing arbitrary prose. OpenAI Platform

6. Use embeddings for semantic understanding
This is another major component.
You take:
REQ-024
"The system should render emergency medical images quickly."
and generate an embedding:
[0.0123, -0.0912, 0.8832, ...]
You store it in PostgreSQL + pgvector.
Then:
REQ-024
       ↓
Embedding
       ↓
Vector Search
       ↓
Find semantically related requirements
For example:
REQ-024
Emergency image rendering

matches:

REQ-061
Diagnostic image processing must complete within 250 ms.

REQ-077
Patient telemetry visualization must not exceed 500 ms latency.

REQ-089
Emergency clinical interfaces must remain responsive during
high patient load.
A keyword search may miss these relationships.
Embeddings can surface them based on semantic similarity.
PostgreSQL's pgvector supports vector similarity search, cosine distance, HNSW and IVFFlat indexes, and can also be combined with PostgreSQL full-text search for hybrid retrieval. GitHub

7. But embeddings alone aren't enough
This is extremely important.
You should NOT do:
similarity > 0.8
        ↓
CONFLICT
That would be another simplistic system.
Instead:
Embedding similarity
        ↓
Candidate relationship
        ↓
LLM semantic comparison
        ↓

        ↓
Logical comparison
        ↓
Conflict confidence
Example:
REQ-031
The system shall automatically lock clinician terminals after exactly 15 minutes of inactivity.
REQ-042
Users shall remain logged in for at least 30 minutes without activity.
Embedding search says:
Highly related
Then your reasoning engine extracts:
REQ-031
timeout = 15 min

REQ-042
timeout >= 30 min
Now the system can determine:
Constraint contradiction
That is a real semantic conflict detector.

8. Build a Requirement Knowledge Model
Every requirement should become structured data.
Something like:
Requirement
│
├── ID
├── Document
├── Section
├── Text
├── Type
├── Category
├── Actor
├── System
├── Action
├── Object
├── Condition
├── Constraint
├── Metric
├── Threshold
├── Priority
├── Dependencies
├── Related Requirements
├── Source Location
└── Embedding
For example:
{
  "id": "REQ-031",
  "type": "security",
  "category": "session_management",
  "actor": "clinician",
  "action": "terminate_session",
  "condition": "15_minutes_inactivity",
  "constraint": {
    "operator": "exactly",
    "value": 15,
    "unit": "minutes"
  }
}
Now you have something far more powerful than raw text.
